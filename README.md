　　TA未送達者におけるJ-LIS照会対応の新規機能構築に伴う影響調査結果

１．はじめに
2022年8月19日にシステム開発調整G様よりご依頼いただきました「TA未送達者におけるJ-LIS照会対応の新規機能構築」について、影響調査を実施いたしました。以下に影響調査結果をご報告いたします。
また、2024年3月12日に追加要件を受領し、2024年3月27日に要件が確定したことから、改めて影響調査を実施いたしました。
　　
２．影響調査依頼の背景
年金給付システムが保持している住所情報と情報システム機構（以下、J-LIS）で管理している住所情報が相違していたことから、一部の者に対して老齢年金未請求書が送られていない（未送達）状況であることが判明した。
本事象に伴い、65歳到達時に送付した老齢年金請求書が未送達となった被保険者に対して、直近の住所情報を取得するため、令和3年11月に保守作業として個人番号によるJ-LIS照会対応を実施し、以後約半年ごとに本対応を保守作業として実施しておりました。
また、老齢年金請求書未送達者と同様にねんきん定期便が未送達となった被保険者に対して、直近の住所情報を取得するため、令和3年1月に保守作業として個人番号によるJ-LIS照会対応を実施し、以後令和4年3月までの月1回ごとに本対応を保守作業として実施しておりましたが、令和5年1月以降より再開するとご指示いただいております。
上記２つの保守作業はどちらもねんきん定期便未送達イベント(INC-SH2-2020-0001494)の業務要件をもとに実施したことから、当該イベントにて作成した資材を利活用し、対応を行っております。

本保守作業について、今後も定期的にJ-LIS照会を必要とする対応が発生することが見込まれていることから、作業工数の削減と手作業による作業ミスの防止を目的として、J-LIS照会対応のシステム化を行うよう基幹システム開発部様よりご指示いただいております。
なお保守作業においてはJ-LIS照会対象者の個人番号特定に係るデータ抽出作業と、J-LIS照会結果による住所情報の更新作業の2つを実施しておりましたが、住所情報の更新に係る機能構築については既に影響調査結果(個人番号住民票情報更新の新規機能構築(INC-SH2-2022-0000238))を提示していることから、本システム化においてはJ-LIS照会対象者の個人番号特定に係るデータ抽出機能のみとするようご指示いただいております。

また、2023年8月9日に「個人番号収録済かつ個人番号住民票情報が未収録である対象者」について、個人番号住民票情報への登録作業を実施しております。
2023年8月以降のTA未送達者ならびにねんきん定期便未送達の対応において、前述の対象者が抽出されていないことが確認されていること、また前述の対象者が登録されるシステム的な契機が既に存在しないことから、業務要件（１）にかかる対応は不要として改めて影響調査を行うようご指示いただきました。

　　
 
３．影響調査依頼の業務要件
　J-LISへ住基情報を照会する対応について、今後の類似イベント等への対応を見込み、汎用的に使用できる機能を構築する。

（１）個人番号収録済かつ個人番号住民票情報未収録者(以下、住民票未収録者)の対応について
過去実施した老齢年金請求書未送達及びねんきん定期便未送達にかかる保守作業では、個人番号管理サブシステムで個人番号と基礎年金番号の紐付情報を抽出し、年金給付システムにて抽出結果をもとに対象者の絞り込みを実施している。
既存処理である「N-I-6-3-1-2 異動者情報照会年金給付システム連携用データ作成」（以下、異動者情報抽出）にて基礎年金番号と個人番号の紐付情報を抽出しているが、異動者情報抽出では個人番号住民票情報をもとに抽出しているため住民票未収録者は抽出されないことから、保守作業においてはSQLにて住民票未収録者の抽出を行い、抽出結果のマージを実施していた。
R4.10以降の対応として、住民票未収録者に対する個人番号住民票情報の登録作業が行われる予定であると伺っていることから、前述の住民票未収録者の対応は以後発生しなくなると考えられるが、個人番号住民票情報の登録作業の実施時期が未定であるため、本システム化においては住民票未収録者の抽出機能についても構築を実施する。
前述の住民票未収録者については、個人番号住民票情報の登録作業を実施済みであり、また住民票未収録者が今後登録される契機が存在しないことから、住民票未収録者の抽出機能は業務要件から除外するものとする。
	
　（２）個人番号と基礎年金番号の紐付情報抽出機能の構築について
過去実施した保守作業では、既存処理の異動者情報抽出を利活用して抽出を実施していることから、本システム化においても異動者情報抽出の資材について利活用が可能か検討を実施した。
既存処理の異動者情報抽出処理では、前月の異動者情報にて生存状況が「死亡」と判定された被保険者についても、J-LISに登録されている生存状況に誤りがあることを考慮して抽出結果へのマージを実施しているが、J-LIS照会を実施するにあたっては現在有効な個人番号の紐付情報のみが必要であることから、保守作業においては死亡者情報のマージ処理の無効化を実施している。
本システム化において既存のジョブネット設定を流用する場合、前述のマージ処理の無効化および走行完了後の復元作業を行うことで実施可能であるが、手作業による作業ミス防止の観点からも新規ジョブネットとすることが望ましい。
また、新規ジョブネットとして定義するにあたり、既存AP資材の利活用を検討したが、異動者情報抽出処理において出力するファイルはジョブ定義のパラメータによらず出力先が固定であること、出力されたファイルは後続処理において参照されるが、既存AP資材を利活用した場合は経常処理の出力ファイルを上書きされるため、対象者情報抽出処理について、新規APの構築が必要となる。
なお、既存の異動者情報抽出処理を改修する案も検討したが、今回（１）に記載している住民票未収録者の抽出論理については、住民票情報登録作業完了後は不要な論理となり、今後経常的に実施される異動者情報抽出処理に対して過渡期的に対応する抽出論理（住民票情報未収録者抽出）が残るのは望ましくないと考える。
また、既存処理を修正した場合においても、関連する異動情報ルートのデグレード試験が必要であること、設計書に関しては現状異動者情報に特化した記載となっていることから、汎用的な記載に修正を行う必要があり、工数としては新規AP構築を構築した場合と既存APを修正した場合で大きく差異がないことから、J-LIS照会を実施するための新規ユースケース処理として機能を構築する。
業務要件（１）が要件から除外されたことから、既存の異動者情報抽出処理との差異としては前述の死亡者情報のマージ処理のみとなるため、既存の異動者情報抽出処理のユースケースに対して既存AP資材を利活用した新規ジョブネットを追加することとする。
既存AP資材を利活用するにあたり、既存AP資材ではファイルの出力要否がジョブ定義のパラメータによらず固定であることから、本対応では参照しない中間ファイルについても必ず出力され、後続処理で参照している既存の異動者情報抽出処理の出力ファイルを上書きする。そのため、ファイルの出力要否を制御できるよう既存AP資材に対して改修を実施する。
（３）年金給付システムへ回付する抽出情報について
年金給付システムへ回付する対象者の抽出条件は以下の通りである。
①、②については異動者情報抽出と同様であるが、本システム化では生存状況が「死亡」と判定された被保険者情報はマージしないこと、また住民票情報未収録者の抽出を実施することから、③を追加している。

①　個人番号、基礎年金番号ともに有効である。
②　個人番号住民票情報の生存状況表示が「生存」または「不明」である。
③　個人番号住民票情報が存在しない場合は、生存状況は「不明」として扱う。

（５）年金給付システムへのファイル連携方法について
異動者情報抽出と同様、HULFT連携にて年金給付システムに連携する。
HULFT-IDについては以下の2案を検討する。
案①：通常通り新規HULFT-IDを付番する。

案②：HULFT-IDについて新規採番は行わず、既存のHULFT-ID：03010119を用いてファイル連携を行う。
既存のHULFT-IDを使用することから、本案件の随時処理は既存処理（異動者情報照会）の照会スケジュールと重複しないよう、日本年金機構様にてスケジュール調整する案である。

検討した結果、案①では年金給付システム側にて実施している後続運用についても新規機能の開発が必要となることから、保守作業時の既存運用と同じく案②で対応を実施する。

（６）エンティティの更新要件について
本システム化ではJ-LIS照会後に個人番号管理情報、個人番号住民票情報、所得照会先市区町村エンティティの更新を行う想定であるが、エンティティの更新には「個人番号住民票情報更新の新規機能構築(INC-SH2-2022-0000238)」案件で構築する機能を使用することとし、本案件として新たに機能構築は実施しないものとする。

（７）J-LIS照会結果ファイルの業務量について
照会対象者の業務量としては、過去保守作業で実施したTA未送達照会対応の件数から、対象者の件数を最大2.4万件とする

（８）処理サイクルについて
日中バッチ処理配下の随時起動ジョブとする。
異動者情報抽出処理については、パーティション毎に抽出処理を行うことから、抽出処理走行中にオンライン処理によって紐付取消ならびに紐付再登録が実施された場合、取消前と再登録後の紐付情報が別々のパーティションから抽出されるタイミングにより同じ個人番号に対する紐付情報が複数抽出される可能性がある。
そのため、既存の異動者情報抽出処理と同様に夜間バッチ処理配下に対象者情報抽出ジョブを配置し、翌日起動する日中バッチ処理配下の抽出情報送信ジョブにて年金給付システムに抽出結果をHULFT送信することとする。
なお、本ジョブはJ-LISの照会要件が発生する毎に起動する処理であることから、リリース時はカレンダ情報に起動日を設定せず、照会対応のスケジュールごとに共通運管業者様により起動日を設定する運用とする。　

（９）DBアクセスログ（Perfログ）の圧縮対応について
現在、保守作業としてねんきん定期便未送達対応等で異動者情報抽出処理を起動した際には、DBアクセスログ（Perfログ）が大量に出力され、DBアクセスログがログ管理サーバに退避される日までの期間中に経常の異動者情報抽出処理（N-I-6-3-1-2）が実施された場合、番号ポータルバッチサーバの容量閾値に達する可能性があることから、作業終了後にログの削除対応を実施しておりました。　　
本案件にてシステム化を実施した際にも、同様の懸念が想定されることから、Perfログの圧縮およびログ削除についても機能として組み込むことを検討しておりましたが、業務AP側でログの圧縮等を実施してしまうと、経常的にHW業者様にて実施いただいているログ管理サーバへの退避に該当ログが組み込まれない形となってしまうことや、今後システム更改に向けて業務側でログ圧縮した容量前提でシステム更改を行われてしまうと、正しい容量設計にならない形で更改されてしまう懸念があることから、業務側でのログ圧縮は行わず、HW業者様のログ管理サーバへの退避に関する仕様（例えば退避するまでの期間を短縮する等）を見直しいただくよう、HW業者様と調整させていただきたいと考えております。

本件については、改めてシステム化の対応を実施する際に、基盤AP保守、HW業者様踏まえご調整させていただきますようお願いいたします。

なお当該事象では番号ポータルバッチサーバの「/var/」ディレクトリにて使用率が80%を超過したことで閾値超過が検知されておりますが、令和4年1月のシステム更改により、ログの格納領域は「/sharevar/log/」ディレクトリへと変更となっております。
当該処理を実行している番号ポータルバッチサーバ2号機について令和6年1月5日から令和6年3月31日までの使用率を確認した結果、保守作業にて異動者情報抽出処理を起動した際に出力されるログによる「/sharevar/log/」の使用率の増分が約4%であることと、保守作業による増分を含めて「/sharevar/log/」ディレクトリの使用率が10%未満であることを確認しております。
また「/var/」ディレクトリについても、本対応における保守作業終了時のPerfログ圧縮および削除対応時に一時的に使用率が24%まで上昇しておりますが、ログ圧縮および削除対応以外の時間帯においては使用率が10%未満であることを確認しております。
そのため、経常処理の出力分とあわせても使用率が80%を超過することはないと想定しておりますが、HW業者様のログ管理サーバへの退避に関する仕様（例えば退避作業に伴い「/var/」ディレクトリ配下の一時フォルダにコピーするため、圧縮後ファイル等とあわせて一時的に2倍の容量を使用するなど）によって閾値超過が発生する可能性については、HW業者様にもご確認いただきますようお願いいたします。
